## PARTE 1: Controle de KM por Planos

### Análise da Proposta

Sua proposta está **excelente do ponto de vista de implementação**. O sistema de planos já suporta perfeitamente essa segmentação. Aqui está a análise técnica:

### Ajuste: Alertas e Analytics no PRO

O usuário confirmou que **alertas automáticos e analytics avançados devem ficar no PRO**, pois a adesão ao MASTER será baixa. A separação ajustada:

| Camada | Starter (BASICO) | PRO | MASTER |
|---|---|---|---|
| **Backend** | Grava em `vehicle_km_history` | + RPC `get_fleet_km_control` + Alertas | + Relatórios avançados |
| **Frontend** | Cards de stats no veículo | + Página `/controle-km` + Alertas | + Exportação + Previsões |
| **Service** | `record()`, `getHistory()`, `getStats()` | + `getFleetKmControl()`, `setWeeklyLimit()`, `checkAndCreateKmAlert()` | + Features premium |

### Estrutura de Planos Existente

O projeto já possui:
- Enum `saas_plan` com valores `BASICO | PRO | MASTER` — exatamente os nomes que você propôs
- Coluna `saas_plan` na tabela `carcontrol_companies`
- Constantes `SAAS_PLAN_LIMITS` em `useCarcontrolUser.ts` com limites por plano
- Hook `useCarcontrolUser()` que expõe `planName` e `planLimits` para toda a aplicação
- Componente `SubscriptionModal` (definido mas não usado ativamente) — pode ser reaproveitado
- Padrão de bloqueio já estabelecido (marketplace usa `checkPlanLimit`, perfil mostra progresso)

### Viabilidade da Implementação

**100% viável.** A separação que você propôs é natural:

#### 2. Route Guard na rota `/controle-km`

Em `App.tsx`, envolver a rota com verificação de plano:

```tsx
<Route path="/controle-km" element={
  <PlanGuard feature="controlPage" fallback={<UpgradeKmPrompt />}>
    <ControleKm />
  </PlanGuard>
} />
```

#### 3. Componente `PlanGuard` (genérico)

```tsx
function PlanGuard({ feature, fallback, children }) {
  const { company } = useCarcontrolUser();
  const plan = company?.saas_plan || 'BASICO';
  const hasFeature = KM_PLAN_FEATURES[plan][feature];

  if (hasFeature) return children;
  return fallback || <UpgradePrompt feature={feature} />;
}
```

#### 4. Guard no service para alertas automáticos

Em `kmHistoryService.ts`, na função `checkAndCreateKmAlert()`:


### Fluxo Completo

```
Usuário clica em "Controle de KM" no menu
  → Rota /controle-km
    → PlanGuard verifica saas_plan
      → Se BASICO: renderiza UpgradeKmPrompt
      → Se PRO/MASTER: renderiza ControleKm

Dentro do ControleKm:
  → KPIs, tabela, filtros: funcionam normalmente (PRO)
  → Editar limite: funciona (PRO)
  → Configurar limites em lote: funciona (PRO)

Ao salvar registro de KM (qualquer plano):
  → kmHistoryService.record() funciona sempre
  → Se PRO/MASTER: checkAndCreateKmAlert() cria notificação
  → Se BASICO: checkAndCreateKmAlert() retorna silenciosamente
```

### Por que essa separação funciona

1. **Sem fricção no Starter:** O básico de gestão de KM funciona. O cliente não se sente bloqueado.
2. **Gatilho de upgrade natural:** Ao ver a página de upgrade com as funcionalidades, o cliente entende o valor do PRO.
3. **PRO como plano principal:** Com alertas e analytics, o PRO se torna o plano mais atrativo para a maioria das locadoras.
4. **Implementação mínima:** 90% das funcionalidades PRO já estão implementadas. Só falta o guard.
5. **MASTER como premium:** Funcionalidades avançadas (exportação, previsões, rankings) para locadoras maiores.

## PARTE 2: Backend do Módulo Lojista

*(mantido do plano original)*

### Diagnóstico

O backend Supabase atual já possui **7 tabelas** e **1 Edge Function** para o marketplace. O módulo lojista usa essas tabelas mas **90% das páginas ainda usam dados mock**. A tabela `marketplace_seller_profiles` e `marketplace_listings` são compartilhadas entre lojistas e o marketplace público.

### Gap: Conceito "Oportunidades" não existe no backend

As "Oportunidades" (demandas de locadoras) são um conceito **separado** dos listings e propostas. O mock mostra:

```ts
{ locadora: "LOC", cidade: "São Paulo", estado: "SP", modelo: "Fiat Pulse", qtd: 5, orcamento: "R$ 600.000" }
```

Isso NÃO é um listing nem uma proposal. É uma **demanda** publicada por uma locadora que o lojista pode aceitar. Precisa de tabela própria.

### Backend Proposto

#### 1. Nova Tabela: `marketplace_demands` (Oportunidades)

Locadoras publicam demandas, lojistas aceitam.

```sql
CREATE TABLE public.marketplace_demands (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  company_id UUID NOT NULL REFERENCES public.carcontrol_companies(id) ON DELETE CASCADE,
  buyer_user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  description TEXT,
  modelo TEXT NOT NULL,
  marca TEXT,
  quantidade INTEGER NOT NULL DEFAULT 1 CHECK (quantidade > 0),
  orcamento_min NUMERIC(12,2),
  orcamento_max NUMERIC(12,2) NOT NULL,
  cidade TEXT,
  estado TEXT,
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','fulfilled','cancelled','expired')),
  validade TIMESTAMPTZ,
  views_count INTEGER NOT NULL DEFAULT 0,
  responses_count INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

#### 2. Nova Tabela: `marketplace_demand_responses` (Respostas dos Lojistas)

Lojistas respondem a demandas com interesse.

```sql
CREATE TABLE public.marketplace_demand_responses (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  demand_id UUID NOT NULL REFERENCES public.marketplace_demands(id) ON DELETE CASCADE,
  responder_user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  responder_company_id UUID NOT NULL REFERENCES public.carcontrol_companies(id) ON DELETE CASCADE,
  message TEXT,
  proposed_price NUMERIC(12,2),
  proposed_quantity INTEGER,
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','accepted','rejected','cancelled')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

#### 3. Nova Tabela: `lojista_analytics_events` (Métricas)

Eventos de tracking para analytics do lojista.

```sql
CREATE TABLE public.lojista_analytics_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  company_id UUID NOT NULL REFERENCES public.carcontrol_companies(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  event_type TEXT NOT NULL CHECK (event_type IN (
    'listing_viewed', 'proposal_sent', 'proposal_received',
    'proposal_accepted', 'proposal_rejected', 'whatsapp_click',
    'demand_viewed', 'demand_responded', 'sale_confirmed'
  )),
  listing_id UUID REFERENCES public.marketplace_listings(id) ON DELETE SET NULL,
  demand_id UUID REFERENCES public.marketplace_demands(id) ON DELETE SET NULL,
  metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

#### 4. Nova Tabela: `lojista_settings` (Configurações)

Preferências do lojista.

```sql
CREATE TABLE public.lojista_settings (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE UNIQUE,
  company_id UUID NOT NULL REFERENCES public.carcontrol_companies(id) ON DELETE CASCADE,
  email_notifications BOOLEAN NOT NULL DEFAULT true,
  whatsapp_notifications BOOLEAN NOT NULL DEFAULT true,
  push_notifications BOOLEAN NOT NULL DEFAULT true,
  profile_public BOOLEAN NOT NULL DEFAULT true,
  show_whatsapp BOOLEAN NOT NULL DEFAULT true,
  show_phone BOOLEAN NOT NULL DEFAULT false,
  auto_reply_enabled BOOLEAN NOT NULL DEFAULT false,
  auto_reply_message TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```
